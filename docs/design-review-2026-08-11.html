Doubtfire — design review

Second pass. The first pass covered visual craft: hierarchy, spacing, type, colour, and copy. This pass adds the four diagnostics a look-only review cannot reach — interaction cost, navigation, keyboard and zoom accessibility, and timing — and reports them together with the first-pass findings.

Everything was verified against the running application with a local database, invented content, and the local preview flag. Contrast ratios, type sizes, spacing values, tab order, reflow at 200 % zoom, animation durations, and the optimistic-tick failure path were measured rather than estimated. Where a defect was reproduced, the report says so.

The single most useful result of this pass: three findings that looked independent in the first pass turn out to be one user-visible failure. The primary action gives no acknowledgment (T1), so a person clicks it twice; the server correctly refuses the second click; and with no error boundary (S1) the refusal becomes an HTTP 500 crash. That chain was reproduced. It is also why H1 — the button sitting above the choice it depends on — is not a matter of taste: it produces a measurable keyboard defect too (A6).

Scope note. This review does not reopen anything settled in docs/adr/. In particular, ADR 0002 holds on every screen — no denominators, no outstanding counts, no lateness. Where a recommendation could be mistaken for a breach of it, the report says why it is not.

What is already correct

Do not break these during the corrective work

Several of these are easy to lose in step 1, which touches nearly every rule in the stylesheet. Some are genuinely good engineering that a visual review would never credit.

  • Text contrast passes everywhere. Every text pair measured between 5.2:1 and 16.7:1. The palette is sound; the contrast problems in this report are borders and controls, not text.
  • Starting a Run is race-safe. run-manager.ts:173 takes a Postgres advisory lock, closes stale Runs, and refuses a second open Run. A double click produces exactly one Run. The data layer is careful — only the interface around it is not.
  • Optimistic ticks roll back correctly. run-flow.tsx:136 queues changes per Task, versions them, and restores the previous state on failure. Verified by stopping Postgres mid-Run: the tick reverted cleanly and an accurate message appeared.
  • Undo is preferred over confirmation. Closing a Run is reversible for 30 seconds and can also be reopened from Home. This is exactly the right trade for a routine action.
  • Error copy follows the rule. "Could not save the change. Try again." states what happened and the way forward, with no blame and no "Oops".
  • Real controls, not styled divs. Buttons are <button>, choices are <label>-wrapped radios, disclosures are <details>. All the free keyboard behaviour is intact.
  • Focus is visible globally. globals.css:69 applies a 3 px cobalt outline to buttons, links, inputs, selects, summaries, and text areas.
  • Transition timing is right. All four transitions run 150–180 ms with eased curves, well inside budget.
  • The decorative image is correctly hidden with alt="" rather than an omitted attribute.
  • Counters use tabular figures, and .formMessage reserves 1.4 em, so neither shifts the layout.
  • Home survives 200 % zoom without horizontal scrolling. Settings does not — see A2.

Root cause

Fix this first. Most of Hierarchy and layout is downstream of it, and fixing those individually without this step recreates the drift.

F1 The design system has no token layer in code High
Symptom

DESIGN.md declares a spacing scale, a type scale, weights, and radii. globals.css declares 13 colour variables and 2 shadows, and nothing else. Every other value is therefore typed by hand where it is used.

Value typeDistinct valuesDetail
font-size34Twelve of them inside a single 4 px band: 11.5, 11.8, 12.2, 12.5, 12.8, 13.1, 13.4, 14.0, 14.1, 14.4, 14.7, 15.7 px
font-weight14520, 540, 600, 650, 680, 700, 720, 730, 740, 750, 760, 770, 780, 800
spacing37About 60 % off the project's own declared scale, including 7, 10, 11, 13, 18, 22, 26, 34, 38, 42, 52, 68, 88, 94, 112, 118 px
Principle

A constrained modular scale creates rhythm. Arbitrary values read as accidental because they are. The difference between weight 720 and 730 is invisible; the difference between fourteen weights and two is visible immediately. (Refactoring UI; Practical UI)

Fix

Add a token layer to :root before any other change, then replace every literal in globals.css with the nearest token. Where a literal is more than one step away, choose the token and accept the change — the nearest-token rule is the point of the exercise.

  --space-1: 4px;   --space-2: 8px;   --space-3: 12px;  --space-4: 16px;
  --space-5: 20px;  --space-6: 24px;  --space-8: 32px;  --space-12: 48px;
  --space-16: 64px; --space-20: 80px;

  --text-xs: 0.75rem;   --text-sm: 0.875rem;  --text-base: 1rem;
  --text-lg: 1.125rem;  --text-xl: 1.25rem;   --text-2xl: 1.5rem;

F2 Two styling systems are installed and neither enforces a scale Medium
Symptom

Tailwind v4 is imported at globals.css:1 and components.json configures shadcn/ui. Exactly one component uses Tailwind — ui/button.tsx:10 — and every class in it is an arbitrary value (rounded-[14px], bg-[var(--cobalt)]), which bypasses the Tailwind scales completely. Everything else is hand-written CSS.

Fix

Choose one and record the choice. The recommendation is to keep the hand-written CSS and drop Tailwind: the interface is small, the class names are already semantic, and the asymmetric island shapes are awkward as utilities. If Tailwind stays, map the F1 tokens into its theme so both share one scale.

Accessibility

PRODUCT.md commits to WCAG 2.2 Level AA. These are measured failures against that commitment, not opinions. A1 to A3 were reproduced in the browser.

A1 Form control borders measure 1.49:1 Blocking
Symptom

globals.css:1319 sets every input, select, and text area border to rgb(16 24 77 / 18%). Over white that composites to #d4d5de — 1.49:1. WCAG 2.2 success criterion 1.4.11 Non-text Contrast requires 3:1 for the visual boundary of a control.

Fix

Use a border measuring at least 3:1 against every background a field sits on. #8a90a8 gives 3.1:1 over white. Verify against --sky, --mint, --lilac, and --ice — fields appear on all four.

A2 Settings requires horizontal scrolling at 200 % zoom Blocking New
Symptom

Reproduced at a 375 px viewport with the root font size doubled: /settings produces a document 423 px wide in a 375 px viewport. WCAG 2.2 success criterion 1.4.10 Reflow prohibits two-dimensional scrolling at this width.

The cause is the settings header: a 46 px back button, the wordmark, a 76 px minimum-width language pill, and a 46 px account control in a flex row that neither wraps nor shrinks. Home escapes only because it has no back button — it is 46 px under the limit, not safe by design.

Principle

Layouts must survive enlargement. Fixed pixel dimensions on text containers overflow the moment a user increases text size.

Fix

Let .appHeader wrap, allow the wordmark to shrink or hide below a threshold, and drop the fixed min-width on the language toggle. Then re-test both headers at 200 %.

A3 Status and error messages are announced to nobody Blocking New
Symptom

Verified by stopping Postgres mid-Run and tapping a Task. The tick applied optimistically, then silently reverted, and .runError appeared with role and aria-live both null. A screen-reader user hears the button announce "pressed", then nothing — the state reverts with no announcement at all.

This is WCAG 2.2 success criterion 4.1.3 Status Messages. ContentForm gets this right; the Run flow does not.

Fix

Give .runError role="alert", and render the container unconditionally so the live region exists before the update. Conditionally mounting a live region does not announce reliably.

States, errors, and recovery

S1 The app has no error, not-found, or loading boundaries Blocking
Symptom

There is no error.tsx, global-error.tsx, not-found.tsx, or loading.tsx anywhere in src/app. Verified against the running app:

  • GET /run/<unknown-uuid> returns HTTP 500.
  • GET /nope returns Next.js's default page: unstyled, English only, outside the design language.

This matters more than usual here — the tablet stays signed in between cleaning days and can hold a stale Run URL.

Fix

Add not-found.tsx and error.tsx in the Doubtfire language, localised through the existing dictionary. Make RunPage call notFound() when the Run does not exist.

S2 Double-clicking "Start cleaning" crashes the app Blocking New
Symptom

Reproduced. The database stays correct — the advisory lock in run-manager.ts:180 means exactly one Run is created — but the second submission throws Error: A Run is already open. and, with no error boundary, returns HTTP 500.

The chain is three findings compounding: no acknowledgment within 100 ms (T1) → the user clicks again → the server correctly refuses → no boundary catches it (S1).

Fix

All three links in the chain deserve fixing, but the cheapest single fix is T1: acknowledge the click and disable the control while the action is in flight. Then give startRunAction and reopenRunFromHomeAction the same ContentFormState treatment ContentForm already uses, so a genuine failure shows next to the button instead of replacing the page.

S3 Archive is a one-way door in the interface High New
Symptom

CONTEXT.md defines Archived as "withdrawn from future Runs while keeping its identity and its history. Content is never deleted." The data model honours that — archivedAt is set, nothing is deleted. But there is no unarchive path anywhere in the application. Confirmed by search: no route, no action, no control.

So an action the domain describes as reversible is, from the household's point of view, permanent. Archiving a Room with twenty Tasks cannot be undone without database access.

Principle

Friction should be proportional to severity, and undo should be preferred to confirmation. Currently the friction is a two-step disclosure — appropriate for a reversible action — while the consequence is irreversible.

Fix

Add an archived-content view in Settings with a restore action. That makes the existing friction correct. If restoring is deferred, raise the friction instead and say plainly in the confirmation that it cannot be undone from the app.

S4 Inert Routine islands look tappable Medium
Symptom

When a Run is open, page.tsx:154 adds .inactive — opacity: 0.72; pointer-events: none. The islands keep their size, fill, icons, and, on the previously chosen Routine, the cobalt selection ring. Nothing says why they no longer respond.

Fix

Replace the list with the open Run's own card, or reduce it to a quiet non-interactive summary and drop the selection ring. Do not leave full-size controls that ignore taps.

S5 A completed Task looks the same as an outstanding one Medium
Symptom

RunTaskControl changes only the 32 px circle. The Task text keeps its full weight, colour, and position, so done work competes with remaining work in a list the user is scanning for what is left.

Principle

Professional work decides what recedes. This does not breach ADR 0002: de-emphasising completed work is not escalating unfinished work, and it introduces no denominator.

Fix

On a ticked row, drop the text to --ink-soft and reduce its weight one step. Do not strike it through, and do not reorder — reordering under a moving finger causes mistakes, and the second device would see rows jump.

S6 The empty state disables the primary action without saying why Medium
Symptom

page.tsx:99 disables "Start cleaning" when no Routine exists. The explanation lives in .homeEmptyState further down the page. The note that used to sit under the button is gone — .availabilityNote and the phaseNote dictionary key are now dead code.

Fix

Put one short line under the disabled button naming what is missing, linking to Settings. Then delete the dead class and key.

S7 The tick error does not say which Task failed Medium New
Symptom

The message is generic — "Could not save the change." — and renders below the whole Task list, at y=413 when the tapped Task was at y=177. In a Room with twelve Tasks the message appears off-screen, and with two people ticking on two devices there is no way to tell which change was lost.

Principle

Put the message where the user is looking, next to its cause.

Fix

Attach the failure to the Task row that failed, and keep a retry affordance on that row.

Timing and motion

This whole section is new. Timing does not appear in a screenshot, which is why it ships unexamined.

T1 The primary action gives no acknowledgment for about a second High New
Symptom

Measured: after clicking "Start cleaning", the main thread was busy for roughly 860 ms before the new screen appeared — on localhost, with a warm dev server and a local database. During that window the button did not disable, did not change colour, did not change its label, and showed no spinner. startRunAction is a plain server action on a <form> with no useActionState or useFormStatus.

Real conditions will be worse: Railway in EU West, a phone on household Wi-Fi.

Principle

Acknowledge every action within 100 ms — that is the threshold at which cause and effect still feel linked. The acknowledgment is not the result. Past it, users cannot tell whether the click registered and click again, which is how double submissions happen. This one produces S2.

Fix

Wrap the Home actions in useActionState and use useFormStatus to disable the button and show a busy label on submit. Do the same for "Mark as done", which already has isClosing available and does not use it visually (A5).

T2 Both entrance animations exceed the 500 ms ceiling Medium New
Symptom
AnimationDurationWhat it animates
care-settle700 msThe Home still life, on every visit
run-rooms-settle520 msclip-path and blur(3px) on the entire Room grid

run-rooms-settle is the more costly of the two: it blurs the Run overview's primary content — the Rooms the user came to tap — for half a second on every render, including every real-time refresh from the other device.

Principle

Anything over about 500 ms feels slow for interface motion, however elegant in isolation. You saw it once; the household sees it several times per cleaning day. Motion earns its place by doing a job — softening a transition, explaining origin, drawing the eye, or making waiting legible. Blurring content that has already loaded does none of these.

Fix

Bring care-settle to about 300 ms. Remove the blur from run-rooms-settle and shorten it to about 250 ms, or drop it entirely — the Room grid does not need an entrance.

T3 No loading boundaries, so route changes show nothing Medium New
Symptom

There is no loading.tsx anywhere. Both /settings and /run/[runId] query the database during server rendering, so navigation to them shows the previous screen until the new one is fully ready.

Fix

Add loading.tsx for both routes, rendering the header and a quiet skeleton of the content shape. Something to look at beats a frozen previous screen.

Checked and correct. All four transitions run 150–180 ms with cubic-bezier(0.16, 1, 0.3, 1) — inside budget and properly eased rather than linear. prefers-reduced-motion gates both keyframe animations. The small transforms that survive the guard (translateY(-2px), scale(1.05)) are the right thing to keep: the user asked for less movement, not less feedback.

Flow and interaction cost

A screen can be well-formed while the path through it is tedious. This section counts actions rather than judging appearances.

L1 The cheaper path through a Run is hidden behind the slower one High New
Symptom

Counted for a realistic Weekly Run — 12 Tasks across 6 Rooms:

PathActionsBreakdown
Room-first (the default)211 start + 1 enter + 5 "Next Room" + 12 ticks + 1 back + 1 mark done
All-Tasks list (hidden)151 start + 1 open disclosure + 12 ticks + 1 mark done
Irreducible minimum12one tick per Task

The flat list is six actions cheaper, and it sits collapsed below six 112 px Room islands, well past the fold.

Principle

Interaction cost is countable, which makes it arguable. Count the actions before defending a flow.

Fix

Not "make the flat list the default" — Room-first has real justification, because people clean room by room and the grouping matches the physical task. The defect is that the alternative is buried. Raise the all-Tasks list to a visible, equal choice at the top of the Run overview, and remember which one the household used last.

L2 Ticking one out-of-order Task costs about six navigation actions Medium New
Symptom

From inside the Bathroom, remembering a Kitchen Task costs: back to grid → scroll → tap Kitchen → tick → back → scroll → tap Bathroom. Rooms can only be reached sequentially through "Next Room" or by returning to the grid; there is no jump between Rooms.

This is not hypothetical for this product — two people clean the same flat at the same time and cross paths.

Fix

Add a Room switcher to the Room screen header — the Room name as a menu, or a compact horizontal Room strip. Fixing L1 also helps, because the flat list makes any Task reachable without navigation.

L3 Home costs a scroll round trip on every Run High
Symptom

The reading order is: greeting → "Choose a routine and start." → [Start cleaning] → the Routine list. The instruction says choose first; the interface presents the action first. At 375 px the button and the third Routine sit about 700 px apart, so choosing a non-default Routine means scrolling down, tapping, and scrolling back up.

It also produces the keyboard defect in A6.

Fix

Move the primary action below the Routine list, keeping the greeting and still life at the top. The sequence then matches the sentence: choose, then start.

L4 At 200 % zoom the Home hero fills the viewport before any functional content Medium New
Symptom

At 200 % the greeting, the instruction, and the still life consume the entire screen. "Routines" is clipped behind the bottom navigation, and the navigation labels themselves are cut off at the viewport edge. The wordmark also collides with the language toggle, and the coral dot overlaps the button.

Because .welcome keeps its 58 % / 42 % split at every size, the copy is squeezed into two-word lines — a measure far below the 45-character minimum.

Principle

A hero that pushes every page's first real content off-screen means each visit begins by scrolling past decoration.

Fix

Collapse .welcome to a single column below a width or above a text-size threshold, and cap the still life's height so the Routine list stays reachable.

L5 The wall tablet is a stated device with no design of its own Medium
Symptom

PRODUCT.md names a wall-mounted tablet used while cleaning. Above 760 px the app renders a fixed 1020 px "phone in a box" — the same 11.5 px navigation labels, the same 32 px tick circles, the same 16 px Task text, viewed from further away and operated with occupied hands.

Fix

This is a product decision, not a CSS tweak, so it is flagged rather than specified. The options are a distinct tablet scale for the Run screens, or a decision that the tablet is a glanceable display and the phone is the input device. Worth settling before the Run screens are restyled in step 6.

Navigation and orientation

N1 The page name does not match the link that leads to it Medium New
Symptom

The navigation item says Settings. The document title says Settings. The page heading says Manage cleaning content. The Home empty state links to the same page with the words Manage Routines.

Principle

The social contract of navigation: the page's name matches the words in the link that led there, exactly. A mismatch makes users doubt they arrived in the right place.

Fix

Pick one name and use it in the nav item, the title, the heading, and every link. "Settings" is the better choice — it is where people expect to find this, and the page manages more than content.

N2 Every Run page is titled "Doubtfire" Medium New
Symptom

/run/[runId] sets no metadata, so the document title falls back to the default. Every Run, every Room, and the completion screen are all "Doubtfire" in the tab, in history, and in the task switcher — on the device most likely to be left open on a screen.

Fix

Add generateMetadata to the Run route using the Routine name, matching the pattern already used by /sign-in and /access-denied.

N3 The Run screens drop global navigation entirely Low New
Symptom

Trunk test from the Room screen: no wordmark, no bottom navigation, no breadcrumb. The header carries a back arrow, the Routine name, and a counter. "Where am I?" is answered only by the Room name; "what else can I do?" is not answered at all.

Fix

A focused mode during a Run is a defensible choice, so this is low severity — but make it deliberate. At minimum restore the wordmark, so the deepest screen still identifies the product.

Hierarchy and layout

H1 The loudest control on the Run overview is the one that ends the Run High
Symptom

markDoneButton is a full-width solid cobalt button — the strongest element on the screen — and it closes the Run. The primary path is entering a Room. A person scrolling to the bottom of the Room list meets the end-the-session control first.

Principle

One primary action per screen; count the solid high-contrast buttons in the viewport and more than one is the defect. The 30-second undo is why this is a hierarchy finding rather than a blocking one.

Fix

Step it down to an outline button or a cobalt text action. Reserve the solid fill for the forward path.

H2 The Room Task screen is the least designed screen in the app High
Symptom

This is where the household spends nearly all its time, and it is the only screen with no colour, no shape, and no continuity. Kitchen is a sky island on the Room grid and a plain white hairline list one tap later. With a short Task list, more than half the viewport is empty below an unpinned button.

Fix

Carry the Room's colour into the screen — a coloured header band is enough. Pin the forward button so its position does not depend on how many Tasks the Room has.

H3 The Settings introduction fills the first viewport Medium
Symptom

.settingsIntro sets the heading to 2.45 rem, so "Manage cleaning content" wraps to three lines. With the description and the link pills the island runs about 660 px on an 812 px screen — 74 % at 200 % zoom. The first Routine sits below the fold on a screen whose only purpose is editing lists.

Fix

Drop the heading to --text-3xl, cut the island padding to --space-6, and let the first manager section start inside the first viewport.

H4 Display type is used for wayfinding Medium
Symptom

.runOverviewHeading h1 and .roomTaskHeading h1 use clamp(2.5rem, 10vw, 4.7rem) — the same treatment as the "Ready when you are." greeting. "Choose a Room" is an instruction, not a greeting. DESIGN.md states its own Short-Display Rule: display type is for short greetings only.

Fix

Use the headline step for both. Reserve display type for Home and the completion screen.

H5 Groups have more space inside them than around them Medium
Symptom
  • Run Room islands: 20–22 px padding inside, 12 px gap between. Inner exceeds outer, so six choices read as one block.
  • Form fields: 7 px from label to field, 14 px between field groups. The ordering is right but a 2:1 ratio at these sizes does not separate anything.
  • Home Routine list: clears the fixed navigation by about 10 px, which reads as a clipped card.
Principle

Gestalt proximity — grouping is read from relative distance. Equal or near-equal spacing destroys the grouping information.

Fix

Room grid gap to --space-6. Form fields: --space-2 inside a group, --space-6 between. Routine section bottom padding to calc(var(--space-20) + env(safe-area-inset-bottom)).

H6 A decorative icon wears the action colour Low
Symptom

roomTaskHeading > svg renders ListChecks at 46 × 46 px in --cobalt beside the Room name. It is decorative and aria-hidden. DESIGN.md reserves cobalt for actions, focus, and active state.

Fix

Remove it, or reduce it to 24 px in --ink-soft.

H7 Group labels outrank the Tasks they describe Medium
Symptom

.runTaskCopy small renders the Group in --cobalt at weight 760, above the Task text. It also repeats on every member rather than heading the cluster once, so two Tasks in "Sink" print "Sink" twice and form no visible group. See A8 for the screen-reader consequence.

Render the Group once as a quiet subheading in --ink-soft above its Tasks, and remove the per-Task eyebrow.

H8 Room colours cycle and imply a grouping that does not exist Low
Symptom

Island colours are assigned by index % 3. With six Rooms, Kitchen and Bedroom are both sky, Bathroom and Koti are both mint. Similarity implies belonging, and here it means nothing.

Fix

Derive the colour from the Room's identity rather than its position, or use one calm fill and let the name carry the distinction. The second option is simpler and costs nothing.

H9 The section-link pills look like controls they are not Low
Symptom

Fix

Remove them on phones, where scrolling costs less than deciding what a pill does. If they stay on wide screens, render them as plain underlined links.

Symptom

How to verify

Run the app with a local database and the preview flag:

DOUBTFIRE_ALLOW_UNAUTHENTICATED_PREVIEW=1 pnpm dev

Check all of these after every step. The last four are the ones a look-only review misses.

  • Scale audit. grep -oE 'font-size: [^;]+;' src/app/globals.css | sort -u | wc -l must fall from 34 to the size of the declared scale. Repeat for font-weight and spacing.
  • Squint test. Blur each screen until text is illegible. The most important element must still stand out and groups must still separate.
  • Solid-button count. More than one solid high-contrast button per viewport is a defect.
  • Contrast. 4.5:1 body text; 3:1 control boundaries and large text. Measure, do not eyeball.
  • Extremes. A 40-character Room name, a 200-character Task, a Run with one Room, a Run with no Due Tasks.
  • Both locales. Finnish strings are consistently longer and break layouts English survives.
  • Keyboard pass. Tab every screen. The focus ring must always be visible and follow visual order — log the y-coordinate of each stop and confirm it increases.
  • 200 % zoom. Double the root font size at a 375 px viewport and confirm document.scrollWidth === clientWidth on every route.
  • Timing. Every action shows a visual change within 100 ms, independent of how long the work takes. Animations under 500 ms.
  • Break it on purpose. Stop Postgres and tick a Task; double-click the primary action; open /run/<random-uuid>. Recovery is where flows actually fail.
